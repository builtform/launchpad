# Supabase — Knowledge Anchor

## Idiomatic 2026 pattern

Supabase is a managed Postgres + Auth + Storage + Realtime + Edge Functions
platform. The 2026 idiom uses the Supabase CLI v3 for local-first development
(local Postgres + Studio via Docker), declarative schemas in `supabase/schemas/`
as the source of truth with migrations generated by
`supabase db schema declarative sync -f <name> --no-apply` into
`supabase/migrations/`, Row Level Security (RLS) enabled on every exposed
table, and TypeScript-generated types via `supabase gen types typescript`.

Caveat on declarative schemas: since CLI v3, pg-delta is the default diff engine
and `supabase db diff` no longer reads `supabase/schemas/` (it diffs the live
local database, so use `db schema declarative sync` instead). pg-delta models
tables, views, materialized views, RLS policies, comments and partitions, but
DML (including storage bucket rows) is never captured and some object kinds
(casts, operators, text search configurations) are not tracked; those still need
seed files or hand-written migrations. Review every generated migration. The
legacy migra engine (opt in with `enabled = false` under
`[experimental.pgdelta]`) has more gaps: view owner and grants,
`security invoker` views, materialized view indexes, `alter policy`, comments,
roles and publications.

Canonical layout:

```
supabase/
  config.toml         # created by `supabase init`
  .gitignore          # created or extended by `supabase init` inside a git repo

# created later, on first use of each feature (NOT by init):
supabase/
  schemas/            # declarative .sql schema files (source of truth)
  migrations/         # timestamped SQL migrations, from `db schema declarative sync`
  functions/          # Edge Functions (Deno), created by `functions new`
    <name>/
      index.ts
      deno.json
      .npmrc
  seed.sql            # optional initial data
.env.local            # SUPABASE_URL + SUPABASE_PUBLISHABLE_KEY for local stack
```

Production-grade pattern adds:

- `lib/supabase/client.ts` — browser client (`createBrowserClient`)
- `lib/supabase/server.ts` — server client (`createServerClient` with cookie
  handling for SSR auth)
- `lib/supabase/proxy.ts`: session-refresh helper called from the root
  `proxy.ts` (Next.js 16+; `middleware.ts` on Next.js 15 and earlier)
- `database.types.ts` — generated types committed to git
- RLS policies in `supabase/schemas/` or `supabase/migrations/` declaring access
  rules per table

Version pins:

- `supabase` CLI v3.x (3.1.x current; binary, or `pnpm add -D supabase`; v2
  stays on the npm `v2.stable` tag, 2.122.x)
- `@supabase/supabase-js@2.114+` (JS client; 2.119 current, and the floor that
  `@supabase/ssr@0.12.7` declares as its peer dependency)
- `@supabase/ssr@0.12+` (SSR adapters for Next, Remix, etc.; still pre-1.0, so
  treat minor bumps as potentially breaking)
- Local Postgres: the init template now sets `db.major_version = 17` (earlier
  CLI releases defaulted to `15`). It must match the remote database's major
  version (check with `SHOW server_version;`), and self-hosted defaults also
  moved to Postgres 17 in 2026. A `config.toml` created by an older CLI may still
  carry `15`.

## Scaffolder behavior

`supabase init` writes `supabase/config.toml` and, inside a git repo, creates or
extends `supabase/.gitignore` (the root `.gitignore` is not touched). It writes
no IDE files unless `-i` is passed. It does NOT create `migrations/`,
`schemas/`, `functions/` or `seed.sql`; those appear on first use of each
feature.

It is **non-interactive by default** in current CLI v3.x. The IDE-settings
prompts ("Generate VS Code settings for Deno?", "Generate IntelliJ Settings for
Deno?") are now opt-in behind `-i, --interactive`, and Deno IDE config moved to
`supabase functions new`. This is the `no-prompts` flavor: invoke plain
`supabase init` and do NOT pipe stdin answers. Flags: `--force` (overwrite an
existing config.toml), `-i/--interactive`, `--use-orioledb`. Global escape
hatches if a future prompt appears: `--yes`, and `--agent yes|no` to override
the CLI's AI-agent detection.

**Pre-bootstrap requirement**: `supabase init` does NOT require auth (no
`supabase login` needed for init alone). Local stack startup (`supabase
start`) requires Docker running; remote project linking (`supabase link
--project-ref <ref>`) requires `supabase login`.

After `supabase init`, the canonical follow-ups (LaunchPad emits these as
post-scaffold customization):

1. `supabase start` — boots local Docker stack (Postgres + Studio + Auth +
   Storage). Skipped at scaffold time; user runs manually when ready.
2. Install JS clients: `pnpm add @supabase/supabase-js @supabase/ssr`
3. Materialize `lib/supabase/{client,server,proxy}.ts` per pattern
4. Generate types: `supabase gen types typescript > database.types.ts` (CLI v3
   targets the local database by default; `--local` is deprecated)

No lockfile from supabase init itself; lockfile from sibling Next.js install.

## Tier-1 detection signals

- `supabase/config.toml` at repo root or under `supabase/`
- `supabase/migrations/` directory with `.sql` files
- `supabase/schemas/` directory with `.sql` files (declarative workflow)
- `package.json` with `@supabase/supabase-js` or `@supabase/ssr` in deps
- `.env.local` with `SUPABASE_URL=` or `NEXT_PUBLIC_SUPABASE_URL=`
- `.env.local` with `*_PUBLISHABLE_KEY=`, or any `sb_publishable_` /
  `sb_secret_` value
- `database.types.ts` generated types file at repo root or `lib/`

## Common pitfalls + cold-rerun gotchas

- `supabase init` is non-interactive by default in current CLI v3.x. Legacy
  guidance to pipe `n\nn\n` into it is obsolete and should be removed from any
  scaffolder wrapper (piped answers are never read). If a prompt ever reappears,
  use the global `--yes` flag. There is no `SUPABASE_INIT_*` env var; the
  init-related env vars are `SUPABASE_WORKDIR`, `SUPABASE_YES` (auto-accepts the
  `-i` prompts) and `SUPABASE_EXPERIMENTAL_STACK` (opt-in experimental native
  stack template).
- `supabase start` requires Docker running and ~3 GB free disk; first start
  pulls multi-GB images.
- RLS is OFF by default on tables created via raw SQL migration; the CLI
  supports `alter table ... enable row level security;` but doesn't add it
  automatically. Forgetting RLS exposes data to anon-key clients — a frequent
  security incident.
- `@supabase/ssr` (v0.12+) replaced the deprecated `@supabase/auth-helpers-*`
  packages; pre-2024 Next.js + Supabase tutorials reference deprecated APIs.
  Within `@supabase/ssr` itself the cookie contract has moved: use `getAll()` /
  `setAll(cookiesToSet, headers)`, never `get`/`set`/`remove`. The published
  type (0.12.x) declares the second `headers` parameter, which carries
  `Cache-Control` and related headers; apply them to the response so CDNs never
  cache a response that sets auth cookies. A one-argument `setAll(cookiesToSet)`
  still type-checks but skips that protection.
- API keys: use the new `sb_publishable_...` and `sb_secret_...` keys. The
  legacy `anon` / `service_role` JWT keys still work but are deprecated by the
  end of 2026. The publishable key is safe for client-side; the secret key
  BYPASSES RLS and must NEVER be exposed client-side.
- Local stack auth emails go to Mailpit (http://localhost:54324) by default; not
  real email delivery until configured. The `config.toml` section is
  `[local_smtp]` (renamed from `[inbucket]` in CLI 2.108.0; CLI v3 refuses to
  load a config that still has `[inbucket]`, so rename it before upgrading).
- Edge Functions run on the Deno-based Supabase Edge Runtime. `npm:` specifiers,
  JSR, and Node built-ins all work without a build step.

## Version evolution

- Supabase CLI v3 (2026-11-02; 3.1.0 on 2026-11-09): breaking major release.
  Database, `gen types` and `storage` commands target the local stack unless you
  pass `--remote`; commands that change a hosted project ask first and need
  `--yes` in CI; flags and `SUPABASE_*` variables override `config.toml`;
  pg-delta is the default diff engine, so `db diff` no longer reads
  `supabase/schemas/`; `[inbucket]` must be `[local_smtp]`; the separate
  `supabase-go` binary is gone. `--linked`, `--project-ref`, `--db-url`,
  `--local` and `gen types --project-id` still work but are deprecated and go in
  v4 (npm `next` is 4.0.0-next.10). Pin v2 with the `v2.stable` npm tag.
- Supabase CLI v2 (2024-2026): renamed many subcommands; declarative schema
  diffing improvements. `--no-verify-jwt` still exists on `functions deploy` and
  `functions serve`, but auth mode is now set at creation time via
  `supabase functions new --auth <none|apikey|user>`.
- 2025-2026: new API keys (`sb_publishable_` / `sb_secret_`) supersede anon and
  service_role; declarative schemas (`supabase/schemas/`) become the documented
  default workflow; Mailpit replaces Inbucket; hosted and self-hosted defaults
  move to Postgres 17; `supabase gen types --lang python` added; the CLI gains
  an `--agent` AI-agent detection flag.
- Supabase CLI v1 (2023): first stable; introduced declarative migrations.
- `@supabase/ssr` (2024): replaces auth-helpers-nextjs/remix/sveltekit;
  cookie-based session refresh.

Track upstream Supabase CLI releases; the scaffolder's prompt flow has shifted
twice in v2.x and is the most-likely freshness-drift surface.
